# hscript-seiun benchmark & verification harness

Two instruments live in this repository: a script-language benchmark (`bench/`) and an
engine-level type-check procedure. Both are used to prove the 1.2.0 rewrite actually made
things faster and did not break the host engine.

## 1. Script benchmark (`bench/Bench.hx`)

```powershell
cd <repo root>                       # .haxelib/hscript-seiun/git
$env:BENCH_LABEL='before'
haxe -cp . -cp bench -D hscriptPos -D CUSTOM_CLASSES `
     --macro "hscript.macros.UsingHandler.init()" `
     --macro "hscript.macros.ClassExtendMacro.init()" `
     -main Bench --interp
```

Then compare two recorded runs:

```powershell
$env:BENCH_COMPARE='before,after'
haxe -cp . -cp bench -D hscriptPos -D CUSTOM_CLASSES `
     --macro "hscript.macros.UsingHandler.init()" `
     --macro "hscript.macros.ClassExtendMacro.init()" `
     -main Bench --interp
```

Configuration is read from environment variables so the harness behaves identically under
`--interp` (which cannot forward argv) and under `-cpp`:

| variable | meaning |
| --- | --- |
| `BENCH_LABEL` | result label; written to `bench/results/<label>.json` |
| `BENCH_COMPARE` | `a,b` - print a per-corpus delta table instead of measuring |
| `BENCH_FILES` | `a.hx;b.hx` - extra corpus files, measured in addition to the built-ins |
| `BENCH_ITERS` / `BENCH_EXEC_ITERS` | initial iteration counts (auto-calibrated) |

### Methodology

* Each corpus is timed separately for **parse** (a fresh `Parser` per iteration, as a host does
  when loading a script file) and **exec** (a fresh `Interp` per iteration, as a host does when
  running a script body).
* Every measurement auto-calibrates its iteration count so one round costs about 120 ms, then
  keeps the **fastest of 9 rounds**. Best-of-rounds is the standard microbenchmark estimator and
  removes the GC/scheduler noise that made single samples on the eval target swing by 2x.
* The parser is configured like the engine configures it: `allowTypes`, `allowJSON`,
  `allowMetadata` all on, and the whole run uses `-D hscriptPos`, which the engine always sets.
* Iteration counts differ per corpus, so **compare ratios, not absolute iteration counts**.

### Corpus

| script | shape |
| --- | --- |
| `gameplay` | typical state/callback script: functions, objects, arrays, switches, string concat |
| `classheavy` | script classes, inheritance, statics, method dispatch (worst case for `new`) |
| `expression` | tight numeric/bitwise loops (interpreter dispatch bound) |
| `shapes` | many distinct small constructs (tokenizer/parser bound) |

`BENCH_FILES` can add real scripts; a failed script is reported as `ERRORED` and does not abort
the run, so a single broken corpus can never invalidate the whole measurement.

### Recorded baseline (pre-1.2.0, eval target, `hscriptPos` on)

`bench/results/baseline.json`:

| script | chars | parse | exec |
| --- | --- | --- | --- |
| gameplay | 7626 | 6.58 ms | 1.99 ms |
| classheavy | 890 | 0.94 ms | 27.48 ms |
| expression | 523 | 0.54 ms | 31.24 ms |
| shapes | 14241 | 18.49 ms | 7.21 ms |
| **TOTAL** | 23280 | **26.54 ms** (857 KB/s) | **67.91 ms** |

TOTAL run-to-run noise is about +/-6%; treat per-corpus deltas below that as noise.

### Acceptance thresholds for 1.3.0

* TOTAL parse >= 25% faster than `baseline`.
* TOTAL exec >= 20% faster than `baseline`.
* no single corpus regressing by more than 10%.

### Result (1.3.0)

The thresholds were checked with a stronger method than `baseline.json` alone: the pre-change tree
was exported with `git archive HEAD` into a scratch directory and **interleaved** with the 1.3.0
tree, seven pairs, same machine, same flags.

| estimator | parse TOTAL | exec TOTAL |
| --- | --- | --- |
| median of 7 runs | 26.38 -> 22.12 ms (**-16%**) | 63.00 -> 39.36 ms (**-38%**) |
| best run | 23.49 -> 21.01 ms (-11%) | 60.60 -> 37.90 ms (-38%) |

Parse therefore **missed** its -25% target (report -11% to -16%); execute beat its -20% target by a
wide margin. `bench/results/baseline.json` was recorded on a quieter machine than the final runs,
which is why its absolute numbers differ slightly from the interleaved HEAD column - always compare
runs taken under the same conditions.

## 2. Engine type-check (integration proof)

From the engine root (`O:\FNF-PsychEngine-0.6.3\FNF-PsychEngine-0.6.3\FNF-SeiunEngine`):

```powershell
lime build windows -Dno-compilation
```

The Haxe phase type-checks the whole engine (including every shadow class generated by
`hscript.macros.ClassExtendMacro`) in a few minutes; hxcpp then starts compiling native C++
(`正在编译第 1/13 组` / `Compiling group 1/13`). **Kill it at that point** - the type-check
result is already complete, and the native build is not needed.

Two things to assert:

1. no `: Error` lines from the Haxe phase;
2. **zero** lines mentioning `hscript/macros/ClassExtendMacro.hx`.

`bench/results/engine_typecheck_baseline.log` is the pristine pre-1.2.0 log. It type-checks
cleanly but contains exactly five deprecation warnings that point into our own macro:

```
ClassExtendMacro.hx:257: characters 21-32 : Warning : (WDeprecated) sound.group = myGroup is deprecated, use myGroup.add(sound)
ClassExtendMacro.hx:239: characters 10-27 : Warning : (WDeprecated) Use preStateSwitch instead of stateSwitched
ClassExtendMacro.hx:257: characters 15-32 : Warning : (WDeprecated) Use preStateSwitch instead of stateSwitched
ClassExtendMacro.hx:239: characters 12-27 : Warning : (WDeprecated) Use postGameStart instead of gameStarted
ClassExtendMacro.hx:257: characters 17-32 : Warning : (WDeprecated) Use postGameStart instead of gameStarted
```

These come from `super.<name>(...)` call sites the macro generates for shadow classes whose
superclass member is `@:deprecated`; the generated expression carries the macro file's own
position. Post-fix, that section of the log must be empty.

## 3. Test suites

```powershell
haxe -cp . -cp test -D hscriptPos -D CUSTOM_CLASSES `
     --macro "hscript.macros.UsingHandler.init()" `
     --macro "hscript.macros.ClassExtendMacro.init()" `
     -main TestMain --interp
```

Individual suites (`TestConformance`, `TestRuntimeExt`, ...) also have their own `main()` and can
be run standalone with `-main <Suite>` for a tighter feedback loop. Run the same command with
Haxe 4.2.5 (`C:\HaxeToolkit\haxe\haxe.exe`) as well as 4.3.7 - the engine supports both.
